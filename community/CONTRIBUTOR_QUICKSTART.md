# Contributor quickstart

Have a concrete problem that could help the next Practitioner? Choose the smallest
useful contribution and make its evidence easy to review. Practice keeps durable
work in Git and uses Buzz for conversation; read the [contribution guidance](../CONTRIBUTING.md)
for the full rules.

## Choose a path

Not sure which type fits? Answer the questions in [the Knowledge Taxonomy](../docs/framework/TAXONOMY.md) before drafting.

- **Correction or Note:** fix an unclear or inaccurate detail, or preserve a bounded observation. Open a focused issue or pull request (PR).
- **Practice:** share a repeatable method with inputs, steps, outputs, evaluation, failure modes, and variations. Start from the [Practice template](../templates/PRACTICE.md).
- **Lab:** propose a reproducible experiment or evaluation. Use the [Lab issue form](../.github/ISSUE_TEMPLATE/lab.yml), then the [Lab template](../templates/LAB.md) for the durable artifact.
- **Story:** document a real implementation with before, intervention, result, and lessons. Complete [the intake and consent record](../templates/INTAKE_CONSENT.md) and [the redaction checklist](../templates/REDACTION_CHECKLIST.md) first, then use the [Story issue form](../.github/ISSUE_TEMPLATE/story.yml) and the [Story template](../templates/STORY.md).
- **Project:** propose open-source software or infrastructure for a defined Practitioner problem. Use the [Project issue form](../.github/ISSUE_TEMPLATE/project.yml).

## Two ways to begin

### Git-native

1. Open the closest [issue template](../.github/ISSUE_TEMPLATE/) and describe the problem, intended user, smallest useful outcome, and evidence or reproduction steps. Use a focused branch for substantial work.
2. Make the smallest reviewable change. Do not include secrets, private data, client material, or unlicensed content.
3. Open a PR linking the issue. State what you checked, what remains uncertain, and any relevant source links or attribution.

### Buzz-first

1. Bring a question, draft, or request for collaborators to the Buzz channel matching the outcome: Learn, Use, Automate, Build, or Transform.
2. Keep the discussion bounded and non-sensitive. When it becomes a proposal, link a Git issue; when accepted, link the merged PR or canonical artifact back to Buzz.
3. Keep Git as the durable review record. Buzz conversation does not approve an artifact or replace its evidence.

## Before opening a PR

- The change solves one concrete Practitioner problem and fits the [contribution model](CONTRIBUTION_MODEL.md).
- Examples, hypotheses, personal observations, and results are labeled accurately.
- The relevant [content](../LICENSE-CONTENT.md) or [code](../LICENSE-CODE) license, [Code of Conduct](../CODE_OF_CONDUCT.md), and safety boundaries are respected.
- Links work, the change is focused, and available checks have been run.

If you are unsure, open the smallest issue or ask in Buzz with the problem, who it affects, and the next decision needed. A maintainer can help route it.
