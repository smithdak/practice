# X4 Handoff

## Status

COMPLETE

## Summary

The autonomy ladder names sixteen automatic demotion triggers and nothing
evaluated any of them. `scripts/demotion_check.py` now enumerates every trigger
by parsing `docs/framework/AUTONOMY_LADDER.md` itself, classifies each one as
evaluable here or not, evaluates the five evaluable ones against the ledger
entries in `ops/ledger/` and the working tree, and reports what fired.

It detects and reports. It does not demote, and it writes no file anywhere.
Removing a promotion from `ops/autonomy/promotions.yaml` is a human act, exactly
as adding one is; that sentence is in the module docstring, in every text
report, and in the JSON as `detects_only`.

The trigger list is never transcribed. Each ladder clause is paired with exactly
one standing `Classification` in the script by keyword signature, and drift in
either direction is a loud exit-2 failure: a clause the ladder adds that no
classification claims, and a classification whose clause the ladder no longer
states. A ladder with no `**Automatic demotion...**` paragraph, no `## A0`..`##
A3` section, or a missing level exits 2 with the file, the anchor, and the fix —
never "zero triggers, all clear".

### The sixteen triggers, each classified

Ids are `<level>-<ordinal within that level's paragraph>`, assigned by the
parser at run time.

**Evaluable here (5).**

| Id | Trigger | How it is evaluated |
|---|---|---|
| A1-2 | a draft edits a path outside the scope named in its assignment | Each path in an entry's `paths_written` against the `write_scope` that same entry recorded at run time, matched with `fnmatch` against the repository-relative POSIX path as `ops/autonomy/operations.yaml` documents. Judged at every level: at A0 the level permits no write, so an empty scope makes any write a violation. |
| A1-3 | a draft changes a `maturity` or `evidence_quality` value | Fires when `paths_written` names a file that currently carries a `maturity:` or `evidence_quality:` field. It detects the write to such a file, never the value change — the ledger records no diff — so the finding names the file for a human to read the diff of. |
| A3-1 | an action taken outside the recorded bound | Fires when the entry records that the run acted (`outcome` completed, failed or reverted, or any path written) while the bound it recorded did not permit it: a precondition recorded `result: fail`, `kill_switch: engaged`, or `promotion: none` while claiming A3. |
| A3-2 | an action taken with no reversal path recorded | Fires when the run acted and `reversal` is absent, blank, under eight characters, or a placeholder. `scripts/ledger.py` refuses to write such an entry; this re-reads it because an entry can reach the repository without passing that validator. |
| A3-4 | an action on an operation since added to the permanently ineligible list | Reads the ids in the ladder's `## Permanently ineligible for A3` table at run time and fires when an entry records a run that acted on one. An id a governance amendment adds is honored without editing this script; a table that cannot be read is reported as unjudged, never as clear. |

**Not evaluable here (11).** Each carries a `basis` naming which kind of "no" it
is, and the full reason is printed in every report.

| Id | Trigger | Basis | Why |
|---|---|---|---|
| A0-1 | `scripts/validate_agents.py` fails on its entry | delegated-to-another-command | The trigger is that command's exit code, already run in CI and by `tests/test_validate_agents.py`. This check never shells out to another validator, so its exit code stays a statement about recorded runs. Its subject is also a registry agent's entry, and every entry reads `not_enabled` while owner gate 6 is OPEN, so no agent holds a level to lose. |
| A0-2 | a packet `Provenance` pointer does not resolve at the recorded `source_commit` | not-observable-in-this-repository | Resolving it means reading the repository as it stood at that commit. This repository holds no packet file, no ledger field names a packet a run produced, and this check reads only the working tree as it stands. |
| A0-3 | a run reads a channel or path outside the scope recorded in its entry | missing-record-field | An entry records `paths_read` but no read scope. Neither the catalog nor the promotion record carries one — `write_scope` is the only bound either states — and channels appear in no ledger field. `docs/schemas/ACTION_LEDGER_SCHEMA.md` already anticipates the missing field. |
| A0-4 | an enablement prerequisite stops holding, such as an escalation route that no longer reaches a human | not-observable-in-this-repository | A file can record that a route is named; no file can record that a person answered. `scripts/steward_readiness_check.py` exists because a human runs that test live. |
| A1-1 | a draft reaches the repository without a human acceptance recorded in the affected Git record | missing-record-field | Nothing links a written path to an acceptance. Phase 4 routes acceptance through a merged pull request, which a checkout cannot see. |
| A1-4 | a packet fails the forbidden-assertion check in `scripts/validate_packet.py` | delegated-to-another-command | That command runs on a packet a human points it at. No packet file exists here and no ledger field names one. |
| A2-1 | a message is posted in a channel absent from `channels.write` | not-observable-in-this-repository | The event is a post in a Buzz channel. The ledger records paths, never channels or messages. |
| A2-2 | a posted message states an action as taken, approved, published, merged, or moderated | not-observable-in-this-repository | Judging the wording needs the delivered message, which is in the channel record, not here. |

| A2-4 | the escalation route named in the entry fails a human-receipt test | not-observable-in-this-repository | A human receipt is an event outside the repository. |

### Beyond the ladder's triggers

The check also reports two things that are not demotion triggers and are
labelled as such in the output:

- **record disagreement** — an entry whose recorded `write_scope` disagrees with
  the catalogued scope, or whose operation the catalog no longer lists. One of
  the two records changed after the run, which makes the scope trigger
  unjudgeable under today's rules until a human says which is right.
- **unjudged record** — a ledger entry that cannot be parsed, or the ineligible
  list being unreadable. Reported rather than counted as clear.

Both exit 1, because both need a human. The rule the `--help` text states is:
exit 0 when nothing fired, 1 when a trigger fired, a record disagreement was
found, or a record could not be judged, and 2 on a usage error including a
ladder this check cannot read.

### Honest cases handled

- An empty ledger fires nothing and exits 0, and the report says the reason is
  that no run has left a record — not that no trigger was found.
- `outcome: refused` with nothing written is the guard working, not a violation;
  so is `dry-run`. A failed precondition alone never fires. Acting *despite* a
  failed precondition does.
- `supersedes` makes the superseding entry authoritative: any `run_id` named in
  any entry's `supersedes` is skipped and listed as superseded, so a chain
  leaves only the last entry judged.
- `SAMPLE_`-prefixed entries are listed and not judged. A hypothetical worked
  example is a document, not a run, and the shipped `ops/ledger/SAMPLE_run.md`
  deliberately depicts a refused run.

## Decisions made

1. **Three-way reason, two-way classification.** The required
   evaluable/not-evaluable split is what the output and the JSON carry, but
   every entry also names a `basis`: `evaluated-here`,
   `delegated-to-another-command`, `not-observable-in-this-repository`, or
   `missing-record-field`. "Another command already does this" and "this is not
   observable from a repository at all" are different facts and a reader acts on
   them differently.
2. **This check never shells out to another validator.** `A0-1` and `A1-4` are
   delegated for that reason. Coupling this exit code to `validate_agents.py` or
   `validate_packet.py` would make a demotion report fail for reasons unrelated
   to any recorded run, and both already run in CI.
3. **`SAMPLE_` entries are not judged.** The ledger schema already distinguishes
   them by name. A sample exists to depict a case, including a bad one, and
   judging it would either force samples to stay benign forever or fire a
   permanent finding on a document. They are listed in the report and in the
   JSON so the skip is visible, not silent.
4. **The maturity detector fires on the write, not the change.** No diff is in
   the ledger, so the honest predicate is "this run wrote a file that carries a
   `maturity:` or `evidence_quality:` field". It over-fires rather than
   under-fires, which is the safe direction for a demotion check, and the finding
   says explicitly that the value change is for a human to confirm.
5. **A record disagreement exits 1 but is not called a fired trigger.** It is
   rendered under `DISAGREEMENT` with a note saying it demotes nothing by
   itself. It still needs a human, because it makes the scope trigger
   unjudgeable for that run.
6. **The demotion target is one level below the entry's `claimed_level`.** The
   ladder's levels are cumulative — an A2 trigger appears in A3's list — so a
   fired clause costs the operation one step, and the finding says "would be
   demoted from A3 to A2". A0 demotes to `not_enabled`.
7. **Scope matching follows the catalog's documented rule**, `fnmatch` against
   the repository-relative POSIX path, where `*` is not special about `/`.
   `scripts/run_unattended.py` uses `fnmatchcase` the same way, so the runner and
   this check agree about what "inside the scope" means. A stricter matcher here
   would report violations the runner would have allowed.

## Risks or unresolved questions

1. **`review_point` has no field to live in, and renewal has no record at all.**
   X1 flagged that promotion entries carry no `review_point`; evaluating the
   ladder's A3-3 trigger needs two things this repository does not have.
   - `ops/autonomy/promotions.yaml` has no `review_point` field. The promotion
     fields `scripts/autonomy_guard.py` requires are `operation`, `level`,
     `write_scope`, `evidence`, `demotion_triggers`, `signed_by`, `signed_on`.
     So no signed promotion can name a review point, and the ledger's optional
     `promotion.review_point` can only ever be copied from a field that does not
     exist.
   - There is no renewal record of any kind. Even with a date recorded, "without
     a renewal record" would have nothing to read.

   Both are needed, and adding only the date would produce a check that fires on
   every promotion past its review point whether or not it was renewed. The
   ladder's A3 section also requires a review point ("hold a review point at
   which the bound is renewed or withdrawn. Silence is not renewal"), so the
   record is missing against the ladder's own standard, not only against this
   check's convenience. **Owner decision, not a tooling change.**

2. **A read scope does not exist either.** A0-3 needs one and no record carries
   one. `docs/schemas/ACTION_LEDGER_SCHEMA.md` already anticipates it. Adding
   `read_scope` to a catalog entry would make A0-3 evaluable for path reads; the
   channel half would stay unobservable.

3. **No acceptance reference links a written draft to a human.** A1-1 needs one.
   The Phase 4 design routes acceptance through a merged pull request, so an
   acceptance reference on the ledger entry (the pull request number, or the
   approving commit) would make the trigger evaluable after X5's workflow lands.

4. **Editing the ladder's demotion paragraphs will fail this check at exit 2.**
   That is deliberate — it is the drift guard — but W2 owns
   `docs/framework/AUTONOMY_LADDER.md` and will edit it. Rewording, adding, or
   removing a clause in any `**Automatic demotion...**` paragraph requires a
   matching edit to `CLASSIFICATIONS` in `scripts/demotion_check.py`. The failure
   message names the clause, the file, and the constant. Adding text elsewhere in
   the ladder, including new rows in the permanently ineligible table, is safe.

5. **`scripts/demotion_check.py` runs nowhere yet.** It adds one failure to
   `tests/test_contract_integration.py::ValidatorWiringTests`, alongside the
   three from X1, X2 and X3. Wiring it into `.github/workflows/ci.yml` (and the
   `checks` target in the `Makefile`) belongs to W2. Both files are outside this
   task's owned paths and were not touched. Suggested CI step:
   `python3 scripts/demotion_check.py --root .`.

6. **Amendment 001's self-modification exclusion is not a separate detector.**
   `community/AMENDMENTS.md` forbids an unattended run from changing any file
   that governs its own bounds. Today A1-2 catches it: no catalogued
   `write_scope` reaches a governing file, and `scripts/autonomy_guard.py`
   refuses a scope that would. A dedicated detector would need a second source of
   truth alongside the ladder, so it is deferred rather than built. Note also
   that the ladder's ineligible table still lists `merge` and
   `publication-and-announcement`, which Amendment 001 makes eligible; A3-4 reads
   whatever the table says, so it will follow W2's edit automatically.

7. **A written path that no longer exists cannot be read.** The maturity
   detector cannot open a file a `reverted` run removed. Every such path is named
   in the report's `Limits` section rather than passed over.

## Deferred opportunities

- **A `read_scope` field on catalog entries**, which would make A0-3 evaluable
  for path reads. It needs an owner decision about what a read bound means for
  an operation whose command reads the whole tree.
- **An acceptance reference in the ledger schema**, closing A1-1 once X5's
  pull-request workflow exists.
- **A renewal record artifact plus `review_point` on a promotion**, closing
  A3-3. Both are governance records, so both are human decisions.
- **A self-modification detector keyed to Amendment 001**, once the amendment's
  file list has a machine-readable home. Putting that list in `ops/autonomy/`
  rather than in prose would let the guard, the runner, and this check read one
  source.
- **A `--since` filter** so a large ledger can be judged over a window. Not
  needed while the ledger holds no run, and `ops/ledger/README.md` records that
  entries are never pruned, so it will matter eventually.
- **A demotion-history record.** This check reports a fired trigger; nothing
  records that a human then removed a promotion. Git history carries it, but a
  reader has to reconstruct it.
