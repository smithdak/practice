## Summary

Issue triage was three prose documents applied from memory: the state machine in
`practices/004-issue-triage.md`, the label mechanics in `.github/TRIAGE_POLICY.md`,
and the intake and escalation routes in `ops/BETA_OPS.md`. Nothing checked that a
triage record carried the evidence its state requires, and nothing stopped an
agent from parking an issue in a state a human owns.

T4 makes the record runnable and the agent boundary machine-checkable. A triage
record is now a markdown file with YAML front matter under `ops/triage/`, and
`scripts/triage.py` checks it offline against the state machine the practice
already defines. Nothing about the human-owned decisions moved: the tool reads
and checks records, and never applies a label, closes an issue, removes content,
restricts a person, or accepts work.

The implemented state machine is exactly the one already written down.

- States `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix` come from
  the Outcome and decision-rules table of `practices/004-issue-triage.md`. The
  entry state `new` comes from the transition table in `.github/TRIAGE_POLICY.md`,
  which routes "New" into the other four.
- Transitions come from that same policy table. The practice's step 6
  ("Re-triage on new information ... A closure may be reopened this way") is
  encoded as `wontfix` to `new`: reopening returns the record to categorize and
  verify rather than jumping straight to a route.
- Evidence per state comes from the practice's decision-rules table, split by
  category where the table splits it (bug versus enhancement into
  `ready-for-human`), plus the policy's "why the scope is bounded" column for
  `ready-for-agent`.
- `wontfix` is the human-owned state: both the label table and the transition
  table of the policy read "Human maintainer only". A record whose `last_actor`
  is `agent` may not sit in it, and no history entry may show an agent making
  the move into it.
- The private-routing categories `safety`, `privacy`, `access`, `conduct`, and
  `legal` are the union of the categories that stop triage in the practice's
  Method step 1 (conduct, safety, access, legal) and the concerns `ops/BETA_OPS.md`
  sends straight to the private intake owner (safety, privacy, access, conduct).
  Such a record must sit in `ready-for-human`, must be owned by
  `private-intake-owner` or `human-moderator`, and may never be actored by an
  agent in any state.
- Role labels come from the `ops/BETA_OPS.md` roles table, the policy's
  maintainer-and-agent table, and `community/MODERATION.md`. `owner_role` is
  checked against that vocabulary, so a personal name is rejected by
  construction.
- Data minimization follows `templates/REDACTION_CHECKLIST.md` section 3 and 4:
  a strict field allowlist, a denylist of identity and message-content field
  names applied at any depth, and a whole-file scan for email addresses,
  handles, phone numbers, and credentials.

`scripts/triage.py next <path>` prints the legal next states, who may apply
each, the owner roles it permits, and the evidence each one requires, so an
agent can prepare a recommendation it has no way to enact. Its output ends with
the boundary statement.

## Decisions made

Task-local only; no locked decision was reopened.

- `subject_ref` is restricted to the literal forms `issue #N` and
  `pull-request #N`. A free-text subject line is the most likely place for a
  member identity or message content to leak into Git, and the issue number is
  enough to find the item.
- A record in `new` carries no `owner_role` and no `evidence`. The practice
  requires categorize and verify before routing, so evidence recorded while the
  record is still unrouted has nothing to support.
- `private_route` is a two-value vocabulary (`code-of-conduct-private-report`,
  `private-intake-route`) rather than free text, so no address, link, or case
  detail can be recorded in a public file.
- The checker verifies the *shape* of `commit_checked`, not that the commit
  exists. Reading git history would break the offline and deterministic
  constraint; the README states this limit plainly.
- `history` is optional, per the task wording. When present it must start at
  `new`, chain, end at the record's `state`, and agree with `last_actor`.
- Directory arguments to `validate` skip `README.md` so `ops/triage` can be
  checked in one command.

## Risks or unresolved questions

- No real triage run exists. `practices/004-issue-triage.md` remains
  `maturity: proposed` with `evidence_quality: none`, and this task changed
  neither field. The sample record is labeled hypothetical throughout and
  contains no real issue, person, or message. Whether the front-matter shape
  survives contact with a real queue is untested.
- `.github/TRIAGE_POLICY.md` says an issue carries at most one state label. The
  checker enforces that within a record, but nothing reconciles a record against
  the labels actually set on a GitHub issue; the two can drift. Closing that gap
  needs a network call, which this task's constraints exclude.
- The personal-data scan is pattern-based. It catches email addresses, handles,
  phone numbers, and credential shapes; it cannot catch a person described in
  prose. The human review in `templates/REDACTION_CHECKLIST.md` remains the
  control, not this script.
- Triage labels themselves are still an owner gate: `ops/BETA_OPS.md` creates
  them only once the repository destination is confirmed. Nothing here asserts
  that gate is cleared.
- `scripts/triage.py` imports PyYAML, as `skills/evals/validate.py` already
  does. CI installs it; a local run without it exits 2 with an install message.

## Deferred opportunities

- A `report` subcommand that prints one ledger line per record so a maintainer
  can audit a batch without opening each file — the practice's "running triage
  log" under Minimal implementation.
- Wiring `scripts/triage.py validate ops/triage` into `.github/workflows/ci.yml`
  and the `Makefile`, so records are checked on every push. Both files are
  outside T4's owned paths.
- An overdue-check-point report: `needs-info` records whose `check_point` has
  passed, which is the practice's stated prevention for the needs-info dead end.
  It needs a date input, so it would take an explicit `--as-of` flag to stay
  deterministic, the way `scripts/check_links.py` does.
- A recorded trial: running the state machine over one real batch and writing it
  up as a Lab would be the promotion evidence `practices/004` names. That is a
  human-owned decision, not an agent's.
