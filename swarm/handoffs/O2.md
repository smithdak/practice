## Summary

Created `scripts/steward_readiness_check.py`, the dry-run readiness checker a
human maintainer runs before enabling the Steward agent. It fills the
operational gap in the "Steward escalation readiness" hold
(`release/OWNER_REVIEW.md`) and the Steward enablement gate of
`release/HOSTED_INSPECTION.md`, which require a passing readiness check with
retained evidence before the identity is enabled. The script inspects
configuration only: no Buzz CLI, no live relay, no keys or credentials. It
exits 0 only when every prerequisite in the fail-closed condition of
`buzz/agents/STEWARD.md` ("Deployment prerequisite: actionable human
escalation") is satisfiable from the provided inputs, and exits 1 with
actionable messages otherwise.

Checks (each mapped to the requirement it operationalizes):

1. Sponsor configured — "The deployment record must name the sponsor
   privately": `--sponsor-role` / `sponsor_role` config takes a role label; a
   real name is accepted only via `--sponsor-name` / `sponsor_name` and the
   output reminds the operator it stays in the private deployment record and
   never goes into the public profile.
2. Member-visible escalation route/label configured — "a member-actionable
   escalation reference in a surface the Steward can see and members can
   use" plus "which published label or route the agent may cite": the value
   must name a published label or route anchored to a Steward-visible channel
   (`start-here`, `ask-practice`, `learn`, `use`, `automate`, `build`,
   `transform`); citing an excluded channel (`foundry`, `maintainers`,
   `announcements`, `projects`, `showcase`) or a direct message fails closed.
3. Human receipt target recorded — "confirm that a human monitors it": a
   non-secret pointer via `--receipt-target` / `receipt_target`.
4. Test receipt confirmed — "configured and tested" and "If the reference is
   absent, inaccessible, or unverified, fail closed": `--confirmed-test-receipt`
   or a dated `test_receipt_date` config field (YYYY-MM-DD, calendar-validated);
   the flag without a date passes with a note to date the retained evidence.
5. Least-membership declaration matches `ops/BUZZ_SECURITY.md`'s Steward row:
   `--membership` / `membership` must equal exactly the seven initial channels,
   with missing, duplicated, excluded, and unknown channels each named in the
   failure output.

Both source documents are re-read at runtime with drift detection: required
anchors (the prerequisite section heading, the sponsor-privacy, member-visible
route, human-monitoring, tested-reference, and fail-closed phrases, and the
membership/exclusion sentences) and the runbook's `| Steward agent |` table row
are parsed and their channel sets compared against the checker's constants; any
parse failure or disagreement exits 1 with a "DRIFT" message instead of
checking against stale assumptions. Inputs that look like credentials, key
material, or email addresses are refused with a "never handles keys or
credentials" message, so the checker is safe to run in any context. `--help`
states it is a prerequisite checker, not an enabler, and that enabling the
Steward stays a human decision and a human action.

## Decisions made

- Derived the five checks verbatim from `buzz/agents/STEWARD.md`'s fail-closed
  condition and the Steward row of `ops/BUZZ_SECURITY.md`; every failure
  message quotes the requirement it enforces so the operator can verify the
  mapping.
- Operationalized "a surface the Steward can see and members can use" without
  a live relay: the escalation route must anchor to one of the Steward's seven
  channels and must not cite an excluded channel or a direct message. A
  Git-only route cannot satisfy the anchor requirement, matching STEWARD.md's
  rule that Git is never an access or private-data intake route.
- Implemented drift detection by pinning exact anchor phrases and the channel
  sets to checker constants; STEWARD.md and BUZZ_SECURITY.md are parsed at
  runtime and any structural change or set disagreement exits 1 with an
  update instruction. Whitespace is normalized before anchor matching so
  line wrapping in prose does not cause false drift.
- Refused secret-shaped inputs (key blocks, password/token/api-key markers,
  email addresses, long `sk-` strings) on all free-text fields, keeping the
  script consistent with its "never handles keys or credentials" contract and
  safe to run in logs or CI.
- Accepted the test receipt via either the flag or a dated config field, with
  the date format strictly validated (no comparison against today, so output
  is deterministic and reproducible).
- Made the config a JSON file with unknown-key rejection (catches typos such
  as `sponser_role`) and command-line flags overriding config values.
- Did not commit: the task's hard rules forbid `git add`/`git commit` for this
  worker; the Director handles commits.

## Risks or unresolved questions

- The checker verifies configuration, not the live hosted surface: it cannot
  confirm the route is actually member-visible or that a human actually
  monitors it. Those remain human inspection duties under
  `release/HOSTED_INSPECTION.md`; passing this script is necessary, not
  sufficient, evidence for the enablement gate.
- Whole-word channel matching can flag a route that merely mentions an
  excluded channel in passing (for example "maintainers rota" alongside a
  valid route). The failure is fail-closed and the message explains the fix;
  rewording the route resolves it.
- The anchors pin exact sentences of STEWARD.md: an editorial rewording that
  preserves meaning will trip drift and require a one-line constant/anchor
  update in the checker. This is intentional (drift detection beats silent
  staleness) but will surface as work on any profile edit.
- The prerequisite evidence itself (sponsor identity, deployment record,
  receipt test) lives outside the repository by design; the checker's passing
  output is only one component of the enablement record.
