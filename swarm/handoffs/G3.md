## Per-practice summary

- **004 — Triage community issues with an evidence-backed state machine.**
  States `needs-info` / `ready-for-agent` / `ready-for-human` / `wontfix`;
  categorize (bug vs enhancement) then verify against the codebase before any
  routing; a decision-rules table requires written evidence per route. Agents
  may label and recommend only; human maintainers own accept and close.
  Failure modes include triaging without verification and invented repro
  steps. Worked example labeled hypothetical.
- **005 — Write release notes from committed evidence.** Entries derive only
  from merged commits, review records, or handoffs; one evidence pointer per
  entry; audience chosen (community vs maintainers); human release-owner
  approval precedes publication; published notes are never silently amended.
  Failure modes include marketing inflation and unverifiable claims.
- **006 — Run a lightweight contributor feedback instrument.** One decision
  question per period, field-to-decision mapping, the ops/METRICS.md
  not-to-collect list as hard exclusions, fixed sampling rules with recorded
  denominators, aggregate-only output, a named human data owner, and signed
  deletion after a stated retention window. Failure modes include
  over-collection, survey fatigue, and leading questions.

## Risks or unresolved questions

- The three methods are proposals with `evidence_quality: none`; none has
  been trialed, and the failure modes are labeled hypotheses. Promotion must
  follow the Wave E trial path plus human review.
- Practice 004 assumes a codebase or artifact set the triager can inspect;
  for the Practice community's own queues, the human-maintainer rotation and
  agent identity boundaries referenced from MAINTAINER_RUNBOOK.md still need
  named humans assigned (L007 already flags that no identities are invented).
- Practice 006's retention window and sampling rule are stated as design
  parameters ("for example"), not fixed values; the data owner must choose
  concrete values at first use.
