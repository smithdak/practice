## Summary

The five agent profiles in `buzz/agents/` described their bounds only in prose, so nothing could check that a running agent stayed inside them. This task adds a machine-readable registry, a validator, and failure-mode tests.

`buzz/agents/registry.yaml` carries `schema_version: 1` and one entry per profile file, each derived from that profile's own text plus the least-membership table in `ops/BUZZ_SECURITY.md`. Every entry records id, name, profile path, one-line mission, autonomy, read/write channel scope (names taken from `buzz/community.json`), the separate-identity requirement, a prohibited list, an escalation route with the human role that owns it, enablement prerequisites, and `status: not_enabled`. All five agents are `not_enabled` because owner gate 6 is recorded OPEN in `release/OWNER_REVIEW.md`; the registry records that fact, it does not change it.

`scripts/validate_agents.py` takes `--root` and exits 0 or 1 with messages that name the file, the agent, the field, and the fix. It fails when a profile has no entry or an entry names a missing profile; when a declared channel is absent from `buzz/community.json`; when an agent declares write access to a private channel or to `announcements` without an explicit `write_approval` record naming an approver role and condition; when a `prohibited` list drops any of the four locked non-negotiables; when `autonomy` is outside `observe`/`draft`/`recommend` (an unattended value gets its own message); when `status` claims enabled while gate 6 still reads OPEN; and when an escalation route or role names a person, handle, or address instead of a controlled role. It also fails closed when it cannot find exactly one `(gate 6)` or `(hold 6)` row to read, because an unreadable gate is not an approved gate.

`tests/test_validate_agents.py` adds 53 tests: one per failure mode above using fixtures built in temporary directories, positive cases proving each check is not vacuous (a reworded prohibition still passes, each attended autonomy level passes, an approved `announcements` write passes), and three tests asserting the real repository passes, that declared profiles exactly match the files on disk, and that every real agent is `not_enabled`.

## Decisions made

Ambiguities were resolved to the narrowest reading the profile text supports. Each is recorded in the registry itself so a reviewer can see the basis:

1. **Write scope defaults to none.** Only the Steward profile states a posting capability ("send a reply in the current assigned channel when appropriate"). The Librarian, Release Editor, Research Auditor, and Guide Maintainer all end their workflows at a draft returned to a human and never state a posting capability, so each gets `write: []`. No agent was given write access to a private channel or to `announcements`.
2. **Autonomy.** The Steward is `recommend`, since it may reply in-channel with a route and one next action. The other four are `draft`. No agent is `observe`, and no unattended level exists. The vocabulary matches the one in `docs/schemas/AGENT_PACKET_SCHEMA.md`, added this phase by another worker.
3. **"None by default" means an empty list.** `ops/BUZZ_SECURITY.md` gives the Release Editor `announcements` "only when assigned a human-reviewed release item; none otherwise" and the Research Auditor "only the public channel or channels named in its approved audit assignment; none by default". Both therefore declare `read: []` and `write: []`. The Release Editor's conditional grant is recorded structurally in `conditional_channels` with its condition and approver role; the Research Auditor's is recorded in `channel_note`, because no source names a specific channel for it to hold.
4. **Roles, not names.** `escalation.owner_role`, `identity.accountable_human_role`, and every approver field use the controlled operating roles from `community/GOVERNANCE.md` and `ops/BETA_OPS.md` (`founder`, `beta-owner`, `continuity-owner`, `maintainer`, `area-maintainer`, `artifact-maintainer`, `release-owner`, `private-intake-owner`, `authorized-inviter`, `agent-sponsor`, `session-facilitator`). Constraining the field to that vocabulary makes "names a person rather than a role" an exact check rather than a heuristic, and it matches the `decision_owner` vocabulary the agent-packet schema uses.
5. **Locked prohibitions are matched by meaning, not by exact string.** Each of the four non-negotiables is satisfied by one entry containing at least one term from each of its required term groups, so an author may reword a prohibition but cannot drop it. A test covers the reworded-but-valid case.
6. **Gate reading fails closed.** The validator locates owner gate 6 and hold 6 by the `(gate 6)` and `(hold 6)` anchors in `release/OWNER_REVIEW.md`. If either anchor is missing or duplicated, it errors and tells the reader to restore the anchor or update the constant, rather than silently treating an unreadable gate as approved.
7. **Agent ids are lowercase slugs** (`steward`, `librarian`, `release-editor`, `research-auditor`, `guide-maintainer`), so `scripts/validate_packet.py` can cross-check a packet's `agent_id` against this file. Verified: that script reads the registry and recovers exactly those five ids.

## Risks or unresolved questions

- **The Guide Maintainer's channel grant is unexplained by its own profile.** `ops/BUZZ_SECURITY.md` gives it membership in `learn`, `use`, `automate`, `build`, and `transform`, but the profile describes only repository-side work: inspecting Guides, referenced Practices, and primary sources. Nothing in the profile says what it reads or does in those five channels. The registry records the runbook's grant as read-only, which is the narrowest reading, but a human should decide before enablement whether the agent needs Buzz membership at all.
- **The registry has no field for non-Buzz capability.** Two profiles imply access outside Buzz: the Research Auditor may "when authorized, locate authoritative primary sources" (network retrieval), and the Librarian "may inspect repository templates and existing public artifacts when access is explicitly provided" (repository read). The channel model does not cover either. Both are recorded as enablement prerequisites requiring a human decision, but the registry cannot currently bound a tool the way it bounds a channel.
- **Two sources of truth for membership.** The Steward's memberships now appear in `ops/BUZZ_SECURITY.md`, in `buzz/agents/STEWARD.md`, in `scripts/steward_readiness_check.py` (as `EXPECTED_INITIAL_MEMBERSHIP`), and in this registry. All four agree today, and the readiness checker already detects drift between the first two. `scripts/validate_agents.py` deliberately does not cross-check the runbook table, so a drift between the runbook and the registry would go unnoticed. See the first deferred item.
- **Anchor coupling.** The gate 6 and hold 6 checks depend on the `(gate N)` / `(hold N)` markers in `release/OWNER_REVIEW.md`. If a future edit renumbers or rewords those rows, the validator fails with an actionable message rather than passing incorrectly, but it will need a one-line constant update at the same time.
- **Person detection is bounded.** The role fields are constrained to a controlled vocabulary, which is exact. Free-text fields (`escalation.route`, `channel_note`) are only scanned for an address or handle shape and for the personal identifiers that appear in this repository. A previously unseen personal name in prose would not be caught.
