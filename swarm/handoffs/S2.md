## Summary

Turned the "bounded packet" every agent profile promises into a machine-checkable contract. `docs/schemas/AGENT_PACKET_SCHEMA.md` defines a packet as YAML front matter plus seven fixed sections, in the house style of the Note and Lab schemas: field table, controlled vocabularies, a table of what a packet may never assert, a numbered list of validator-enforceable rules, and a worked example labelled hypothetical. `templates/AGENT_PACKET.md` is the fillable form. `scripts/validate_packet.py` enforces the contract offline and deterministically, and `tests/test_validate_packet.py` covers every rejection path with temporary-directory fixtures.

The contract is deliberately narrow where the human boundary lives. `human_decision_required` must be `true`, `status` must be `draft`, and `decision_owner` must be one of the controlled operating roles from `community/GOVERNANCE.md` and `ops/BETA_OPS.md` — a personal name is rejected. Every claim bullet under "What the evidence shows" must carry a repository path that resolves under `--root` or a source URL with an as-of date; a "Recommended action" section holds exactly one action plus a `Verification:` line a human can run without agent privileges; and visible prose that asserts a promotion, a maturity or `evidence_quality` change, a cleared gate, a lifted hold, or that human review is unnecessary is rejected. A negation earlier in the same sentence suppresses that last check, so a packet can still record that a gate is *not* cleared, and a refused instruction can be preserved verbatim inside a fenced code block without the packet asserting it.

The `agent_id` cross-check against `buzz/agents/registry.yaml` is tolerant by design, because S1 was writing that file in this same tree while this task ran. When the file is absent, unparsable, or lists no recognizable identifiers, the check is skipped with an informational note on stdout and the packet can still pass. The registry landed during this task and the check now works against it unchanged: the extractor reads S1's `agents:` list of `id:` entries and reports `guide-maintainer, librarian, release-editor, research-auditor, steward`. No file under `buzz/` was created or edited by this task. S1 and this task converged independently on the same `observe`/`draft`/`recommend` autonomy vocabulary and the same role vocabulary, so the two artifacts agree without coordination.

The schema's worked example is a hypothetical research-auditor freshness check with no real person, member, or Buzz message in it. It was extracted from the document and run through the validator against the real repository root: 0 errors.

## Decisions made

- **Front matter is real YAML, parsed with PyYAML.** `inputs` is a list of mappings, which the repo's hand-rolled front-matter reader in `scripts/validate_artifacts.py` does not parse, and the registry is an arbitrary-shape YAML file written by another worker. PyYAML is already a CI dependency for `skills/evals/validate.py`. The validator normalizes the `datetime.date` objects PyYAML produces from unquoted ISO dates.
- **`decision_owner` is an enum, not a heuristic.** "A role, not a name" is only mechanically checkable against a controlled vocabulary. The eleven values are taken from the roles already named in `community/GOVERNANCE.md` and the "Roles (roles, not names)" table in `ops/BETA_OPS.md`; no new role was invented.
- **`source_commit` must be a hexadecimal commit.** A packet built against an uncommitted tree cannot be reproduced by its reviewer, so there is no `working-tree` escape value.
- **Forbidden-assertion patterns are narrow and negation-aware.** Broad matching on words like "promoted" or "gate" would reject honest sentences. The patterns require an affirmative verb form, are checked against visible prose only (code fences and inline code are masked), and are skipped when a negation appears earlier in the same sentence. The trade-off is documented in the schema so an author can predict a rejection. The sentence-bounded window matters: an earlier line-bounded version was silenced by the literal word "not" in the heading "What is not established".
- **Two cross-checks beyond the stated requirements**, both cheap and audit-useful: "Decision requested from a human" must literally name the `decision_owner` role, and "Provenance" must account for every `ref` declared in `inputs`.
- **Registry shape tolerance over strictness.** The extractor accepts `agent_id:` or `id:` keys at any depth and the keys of an `agents:` mapping. A registry that parses but yields no identifiers skips the check rather than failing, so a future reshaping of that file cannot break packet validation for reasons a packet author cannot fix.

## Risks or unresolved questions

- **Nothing runs `scripts/validate_packet.py` in CI.** `.github/workflows/ci.yml` and `Makefile` are outside this task's owned paths, and no packet files exist in the repository yet, so there is nothing to scan. Wiring is a Director decision — including whether packets are ever committed to Git or stay in the private maintainer record, which this task did not decide.
- **The CI workflow comment "Only skills/evals/validate.py needs a third-party package" is now inaccurate**, since `scripts/validate_packet.py` also imports PyYAML. CI already installs PyYAML, so nothing breaks; the comment is stale. `.github/workflows/ci.yml` is not an owned path.
- **The template's default `agent_id: agent-id` is deliberately not a registered identifier**, so a template filled in without changing it fails the registry cross-check with an actionable message. A front-matter comment points at `buzz/agents/registry.yaml`.
- **`agent_version` has no source of truth.** Agent profiles in `buzz/agents/` are not individually versioned and the registry records no per-agent version, so the field records the operator's version for the running agent. The schema says exactly that rather than implying a versioning scheme that does not exist.
- **No packet was produced by an actual agent run.** Every packet exercised here is a fixture or a labelled hypothetical example. Whether the seven sections are the right shape for real agent output is unproven until a real bounded run fills one in.
- **The schema's worked example is not regression-tested.** It validates today (checked by hand, recorded above), but nothing fails if a future edit to `practices/001-context-pack.md` breaks the cited path. A test asserting on live repository contents was avoided to match the fixture-only convention in `tests/`.

## Deferred opportunities

- **Machine-check `autonomy` against the registry's per-agent autonomy bound.** `buzz/agents/registry.yaml` records an `autonomy:` value per agent, so a packet claiming more autonomy than its registry entry allows could be rejected mechanically. Not implemented here because it couples this validator to another worker's field layout mid-flight; the schema records it as a human review point instead.
- **A packet index or ledger.** Uniqueness of `packet_id` is only enforced across the paths passed to one invocation. A committed ledger, or a convention that packets live in one directory the validator can glob, would make uniqueness and supersession chains checkable across time.
- **Verify `source_commit` exists in the repository.** The validator checks the shape of the hash, not that `git cat-file` resolves it. That check needs a git subprocess, which conflicts with the offline, deterministic, standard-library constraint applied here.
- **A `docs/schemas/` index.** Seven schema documents now sit in that directory with no README pointing a newcomer at which one governs what. Outside this task's owned paths.
- **Cross-reference the packet contract from the profiles.** Each of the five `buzz/agents/*.md` profiles still defines its own bespoke `text` output block. Those blocks and this schema now describe overlapping shapes; reconciling them — either by making the profile blocks the section content of a packet, or by explicitly scoping each to its channel — is a follow-up on files this task does not own.
