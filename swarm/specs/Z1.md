## Fixed interfaces

1. **`review_point` is a required promotion field.** Add it to `REQUIRED_PROMOTION_FIELDS` in `scripts/autonomy_guard.py`. It is an ISO date strictly after `signed_on`. The shipped file keeps `kill_switch: engaged` and `promotions: []`; only its header comment changes, to list the new field and to state that a renewal is a separate record.
2. **A renewal is a new record, never an edit.** `ops/autonomy/renewals.yaml` ships as `schema_version: 1` and `renewals: []`. Each entry has exactly these fields: `operation` (an id with a promotion in `promotions.yaml`), `promotion_signed_on` (the `signed_on` of the promotion it renews, so the pair identifies the promotion), `renewed_on` (ISO date, not in the future, not before the promotion's `signed_on`), `review_point` (ISO date strictly after `renewed_on`), `signed_by` (a controlled operating role, the same vocabulary the guard already applies to promotions), and `reviewed` (a non-empty list of repository paths a reviewer can open; each must exist). Editing a promotion's own `review_point` after signing is not a renewal; say so in the file header and the README.
3. **Three new guard preconditions**, named so the ledger can record them: `review-point-recorded` (present, ISO, after `signed_on`); `renewal-record-readable` (`renewals.yaml` exists, parses to a mapping with exactly the two top-level fields, every entry is well-formed, every entry names a promotion that exists; a missing, unreadable, or malformed file refuses every operation, like the promotion record does today); `review-point-not-passed` (the as-of date is on or before the effective review point). The effective review point is the promotion's own `review_point`, or the `review_point` of the latest renewal for that promotion whose `renewed_on` is on or before the as-of date. A renewal dated after the as-of date is ignored for that date. The refusal text for a passed review point must say that silence is not renewal, matching the ladder.
4. **The runner records the effective review point.** `scripts/run_unattended.py` writes `promotion.review_point` as the effective value the guard computed, not the raw promotion field.
5. **The ledger requires it when a promotion is recorded.** In `scripts/ledger.py`, `review_point` moves from `PROMOTION_OPTIONAL` to `PROMOTION_REQUIRED`; an entry recording `promotion: none` is unchanged. Update the promotion table and the trigger table in `docs/schemas/ACTION_LEDGER_SCHEMA.md`. `ops/ledger/SAMPLE_run.md` records `promotion: none` and needs no change.
6. **The demotion check evaluates A3-3.** `acted-after-review-point` becomes `evaluable=True`, `basis=BASIS_EVALUATED`, with a detector: an acting entry whose `run_date` is after its recorded `promotion.review_point` fires the trigger, unless `renewals.yaml` carries a renewal for that operation with `renewed_on` on or before `run_date` and `review_point` on or after `run_date`, in which case the finding is a record disagreement (the run recorded a stale review point). An acting entry that claims A3 and records no `review_point` is reported as an unjudged record, never counted as clear. Keep the classification's `tokens` matching the ladder clause; replace the reason text. `classify_triggers` must still pair every clause exactly once.
7. **Documents that describe the records.** `ops/autonomy/README.md`: the guard-check table gains the three preconditions; "How a promotion would be made" states the review point and where a renewal is recorded; "How to reverse it" stays kill switch first. `ops/autonomy/PROMOTION_PROPOSAL.md` section 9 names the renewal file and its fields. `ops/autonomy/PR_REVIEW_CONTRACT.md` names the renewal file where it names the review point. `ops/OPERATING_LOOP.md`'s record table gains a row for the renewal record.
