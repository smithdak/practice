## Summary

Added `tests/test_buzz_parity.py`, a stdlib-only unittest suite (8 tests) that
asserts `buzz/community.json` matches the channel information architecture in
`buzz/INFORMATION_ARCHITECTURE.md`. The suite derives the documented channel
set from the doc by parsing it, then checks name-set equality, visibility
mapping, channel and visibility counts, stream type, distinct topic/purpose,
canvas/seed path existence and distinctness, and the one-marker idempotency of
every seed. It passes on the current repo state; no doc or JSON edits were
needed, so no inconsistency had to be reported.

## Decisions made

Parsing strategy (the core decision): the doc's structured channel data lives
in the "Channel map" markdown table, so the test locates the `## Channel map`
section, extracts pipe-table rows, skips the separator row, validates the
header is `[Channel, Access, ...]`, and yields `(name, access)` pairs with
backticks stripped. Number words in prose ("twelve Buzz channels: two private
... ten open", and "twelve stream channels" in `release/LAUNCH_CHECKLIST.md`)
are parsed through a `WORD_TO_INT` table instead of hardcoded integers, so a
deliberate count change in the docs updates the expectations. Drift in doc
structure (missing section, renamed header, unparseable count word, ambiguous
checklist phrase) fails with a message naming the fix, per Wave-A acceptance.

Doc ↔ JSON mapping decision (doc and JSON legitimately differ in structure):
the "Channel map" table documents only name and access level; the "Launch
decision" section adds totals and "every channel is a stream"; the "Channel
lifecycle" section requires each channel to have a distinct name, topic,
purpose, canvas, and idempotent seed without enumerating them. Per
`buzz/BOOTSTRAP_RUNBOOK.md`, `buzz/community.json` is the canonical
configuration for topic, purpose, canvas, and seed. The test therefore encodes:

- doc table `Channel` ↔ JSON `name` (set equality, no duplicates);
- doc table `Access` ↔ JSON `visibility` via the explicit map
  `{Private: private, Open: open}`;
- doc "twelve/two/ten" and checklist "twelve stream channels" ↔ JSON channel
  count and per-visibility counts;
- doc "Every channel is a stream" ↔ JSON `type == "stream"` on all channels;
- doc "distinct name, topic, purpose, canvas, and idempotent seed" ↔ JSON
  non-empty, pairwise-distinct `topic` and `purpose`, pairwise-distinct
  `canvas`/`seed` paths that exist on disk, and exactly one
  `practice-seed:<id>` marker per seed file (matching the
  `practice-seed:` marker contract used by `scripts/buzz_bootstrap.py` and the
  launch checklist).

Topic and purpose *text* is intentionally not compared to prose: no such text
exists in the doc, and comparing JSON to the table's "Distinct outcome" column
would assert a paraphrase relationship no document states.

## Risks or unresolved questions

- The doc table and JSON deliberately share no topic/purpose strings, so this
  suite cannot catch a wording-only edit to JSON topics/purposes; it catches
  missing, empty, or duplicated values. A future doc column carrying canonical
  topic/purpose text would make exact-text comparison possible.
- `python3 scripts/validate.py --task A3` stays red until the manifest wiring
  task appends A3; the release validator is unaffected (it passed).
- The checklist parser requires exactly one `N stream channels` phrase in
  `LAUNCH_CHECKLIST.md`; if launch prose later adds another such phrase, the
  test fails with instructions rather than guessing.
