## Summary

Created `release/HOSTED_INSPECTION.md`, the checklist an authorized human runs
after the owner-operated bootstrapper apply to confirm the hosted Buzz surface
matches `buzz/community.json`. It fills the "Hosted member-visible surface"
hold in `release/OWNER_REVIEW.md` — the gap the onboarding dry run found
(configuration present, hosted evidence absent) — without asserting that the
apply has happened or that any gate is cleared.

Structure: preconditions (authorized operator, apply mode including
`--skip-seeds`, exact configuration commit ID, private-channel access,
text-only evidence recording); evidence rules stating what to retain and what
must never be recorded; a fillable per-channel table covering all twelve
channels (existence as stream, observed visibility, topic/purpose match,
non-empty canvas, observed seed marker with expected `<channel>-v1` labels);
membership spot-checks against the least-membership table in
`ops/BUZZ_SECURITY.md` (per-agent expected memberships, no owner-level or
moderation authority, no shared identities); the `start-here` member-path
check from a plain member view; the Steward enablement gate (expected
disabled; active only with passing `scripts/steward_readiness_check.py`
evidence); failure handling that stops and records with human recovery paths;
and a role-based sign-off referencing `release/GATE_EVIDENCE.md` and the
release-evidence template.

## Decisions made

- Referenced `release/GATE_EVIDENCE.md` and `scripts/steward_readiness_check.py`
  as inline code rather than markdown links, because O1 and O2 own those files
  in parallel and they do not exist yet; a markdown link would break
  `check_links.py` until they land.
- Recorded the expected seed marker labels as `<channel>-v1` (verified against
  all twelve files in `buzz/seeds/`) so the inspector can compare observed
  values, while still requiring the row to record what was actually observed
  or `unverified` — the marker is an HTML comment the hosted UI may not
  render, so the checklist allows confirming it from the retained apply report
  instead of inventing a UI feature.
- Scoped the `start-here` check to a read-only plain-member view (channel,
  topic, purpose, canvas, seed template visible) and pointed the interactive
  post-and-follow-up test at the private-beta orientation item in
  `release/LAUNCH_CHECKLIST.md`, because posting a test message would leave
  member-visible content that the no-deletion recovery rule cannot clean up.
- Kept membership evidence to channel-name sets, agent roles, and human
  presence counts; sponsor identity and member names stay in the private
  access inventory, matching the evidence boundary in
  `templates/RELEASE_EVIDENCE.md`.
- Added an explicit "extra channel / forum channel / unexpected workflow" set
  check: the apply never creates these, so their presence is recorded as a
  finding for human review rather than an inline fix.

## Risks or unresolved questions

- The checklist is unexercised: the first real post-apply inspection may show
  that some hosted UI does not expose message source (making marker
  confirmation report-dependent) or that private-channel row inspection needs
  a different access path than assumed.
- `scripts/steward_readiness_check.py` does not exist yet (O2 owns it); the
  Steward gate row stays `not-run` until that script and its evidence exist.
- The "Hosted member-visible surface" hold remains OPEN; only a human running
  this checklist after a real apply can produce the clearing evidence.
