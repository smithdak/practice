## Summary

Built the action ledger: the record an unattended run leaves behind, so a run
that ever happens is auditable and reversible after the fact. One entry is one
markdown file with YAML front matter at `ops/ledger/<YYYY-MM-DD>-<run_id>.md`,
recording the run id, operation, actor, the level the run claimed, the trigger,
the promotion record and kill-switch state observed at run time, every
precondition checked with its result, the paths read, every path written, the
write scope the run was bound to, the reversal, the outcome, and the schema
version.

`scripts/ledger.py` does two things. `validate <path...> [--root]` checks
entries or directories of them (exit 0 valid, 1 violation, 2 usage). `append`
writes one entry from structured input, either as a Python call
(`append_entry(entry, ledger_dir=None, root=..., body=None) -> Path`) or as
`append --entry run.json`, so X3's runner records a run without reproducing the
format. `append_entry` validates before writing and refuses to overwrite an
existing entry, because the ledger is append-only.

Three properties matter to the phase invariant. An entry is a record and never
an authorization — the schema, the validator's own output, and the default body
all say so in those words. The ledger deliberately does **not** reject an entry
whose written paths fall outside its write scope, or one claiming A3 with the
kill switch engaged: those are real records of a demotion trigger, and a
validator that rejected them would make the worst case the only case the ledger
could not record. Judging them is X4's demotion check and a human's. The
committed sample depicts a **refused** run, not a promoted one.

## The interface X3 calls

```python
import sys
from pathlib import Path

sys.path.insert(0, str(Path(__file__).resolve().parent))
from ledger import LedgerError, append_entry, next_run_id

written = append_entry(entry, root=root)   # Path of the new entry, or LedgerError
```

`next_run_id("cadence-snapshot", root=root)` returns the next unused
`<operation>-NNN` by reading the file names already in the ledger, so two runs
never collide and `supersedes` names exactly one entry. `render_entry(entry)`
returns the markdown a dry run would have appended without writing it.
`LedgerError.violations` is the list of actionable strings, and
`LedgerError.report()` is the message plus one line per violation. The full
field table and the rules are in `docs/schemas/ACTION_LEDGER_SCHEMA.md`.

## Decisions made

- **Level vocabulary is `A0`-`A3`, not the packet values.** The catalog records
  `level: A1`, so entries use the same ids. `observe`, `draft`, and `recommend`
  are rejected in `claimed_level` with a message saying they are packet values,
  not level ids.
- **`write_scope` is recorded in the entry, not looked up later.** A reviewer
  reading an entry in a year should not have to reconstruct what the catalog
  said that day, and a bound may have been withdrawn since.
- **Existence is checked for written paths only, and only when the outcome is
  `completed`.** `paths_read` is not existence-checked: a later commit may
  remove a file a past run read, and the entry is a historical record, not a
  live index.
- **`refused` and `dry-run` may list no written path**, and a `refused` entry
  must name at least one failed precondition. A refusal nobody can trace is not
  a record, and this is the rule that keeps the inert case from being recorded
  as anything else.
- **Outcome vocabulary is `refused`, `dry-run`, `completed`, `failed`,
  `reverted`.** `failed` and `reverted` deliberately do not require written
  paths to exist, because a partial write may have been cleaned up and a
  reversal may have removed the file.
- **Precondition ids are the guard's vocabulary, not the ledger's.** The ledger
  checks slug shape, a `pass`/`fail` result, a non-placeholder detail, and no
  repeated id. Which checks exist is X2's business, so the two components can
  change independently.
- **The catalog cross-check is skipped when the catalog is unreadable**, with an
  informational line rather than a failure, matching how `validate_packet.py`
  treats a missing registry. This is what let X1 finish while X2 was in flight.
- **Phase-4 sibling paths are named in inline code, not linked.** The schema and
  README reference `ops/autonomy/operations.yaml`, `promotions.yaml`,
  `scripts/autonomy_guard.py`, `scripts/run_unattended.py`, and
  `scripts/demotion_check.py` without markdown links, so a link check cannot
  fail on a file another worker had not written yet. Upgrading them to links is
  a one-line change per reference once the phase lands.

## Risks or unresolved questions

- **CI wiring is unfinished and is W2's.** `tests/test_contract_integration.py`
  fails for `scripts/ledger.py` (and for X2's guard) until the workflow runs it.
  The step to add to `.github/workflows/ci.yml`, next to the triage step, is:
  `- name: Ledger entries` / `run: python3 scripts/ledger.py validate ops/ledger --root .`.
  It is safe as a gate: it validates the committed sample and exits 0 on an
  otherwise empty ledger, printing that an empty ledger is the expected state.
  Adding a `make ledger` target beside `make triage` is the matching Makefile
  change. Both files are W2's.
- **No review point exists to record, so one ladder trigger is not checkable
  from the ledger alone.** The ladder's R4 requires a review point at which a
  bound is renewed or withdrawn, but the promotion entry shape X2 shipped has
  exactly seven fields and no review point, so a runner has nothing to copy.
  `promotion.review_point` is therefore optional in an entry: when a promotion
  ever carries one, X3 should record it, because the ladder's "acted after the
  review point without a renewal record" trigger is otherwise invisible to X4.
  Adding the field to the promotion record is a governance-record change, not
  something this task could make.
- **The validator cannot tell whether `paths_written` is complete.** It checks
  that what is listed exists; it cannot detect a path the run touched and did
  not record. Completeness comes from X3 writing the list from its own bounded
  write path, not from validation. That limit is stated in the README so no
  reader mistakes a valid entry for proof of full disclosure.
- **`trigger` has exactly two values, `schedule` and `manual`.** If X5's
  workflow needs to distinguish a dispatch from a cron run, that is a schema
  version change, not an edit; the rule is stated in the script and the schema.
- **`kill_switch` in an entry is a copy, not a reading of the live record.** It
  records what the run observed, which is what an auditor needs; it is not
  evidence of the current state. Anyone checking whether the substrate is inert
  today reads `ops/autonomy/promotions.yaml`, not the ledger.

## Deferred opportunities

- A `ledger summarize` subcommand printing one line per entry — date, operation,
  outcome, paths written — so a maintainer can read a month of runs without
  opening files. Not built: nothing to summarize while the ledger is empty.
- Cross-entry checks that a `supersedes` target exists in the same directory and
  that no entry is superseded twice. Left out because a single-file validation
  run cannot see siblings, and a false failure on a legitimate one-file check is
  worse than the missing check.
- A `--json` output mode for `validate`, so a workflow can post violations into
  a pull request comment without parsing prose.
- Recording the runner's own exit code and duration in the entry. Useful for
  operations work, but neither is needed to answer what a run read, changed, or
  how to undo it, and every field added to a record is a field a runner can get
  wrong.
