# X3 Handoff

## Status

COMPLETE

## Summary

`scripts/run_unattended.py --operation <id> --root . [--dry-run]` connects the
guard to the ledger and makes `write_scope` mean something at execution time. It
exits 0 on a completed or dry run, 1 on a refusal or a failure, and 2 on a usage
error.

**The guard decides.** The runner calls `scripts/autonomy_guard.py` first and
reimplements none of its twenty-four preconditions: it calls that module's own
`evaluate()` and `render()`, prints the guard's message verbatim, and treats a
non-permitted decision exactly as the guard's `main()` does — as exit 1. A guard
that raises is a refusal. A refusal still appends a ledger entry with
`outcome: refused`, because an unrecorded refusal is indistinguishable from a run
that never happened.

**The runner enforces the bound.** The catalogued command never executes against
the repository. It runs with its working directory set to a staging copy of the
root, made in a `mkdtemp` directory. The tree is fingerprinted (path, symlink
target, SHA-256 of each file) right after the copy and again after the command
exits; the difference is what the command created, changed, or deleted. Results
are applied **only** when every touched path matches `write_scope` under the
`fnmatch` semantics the catalog documents. If any path falls outside the scope,
if anything was deleted, if a changed path is a symlink, or if the command exited
non-zero or timed out, nothing at all is copied back: the staging copy is
discarded and the run is recorded as `failed`. Out-of-scope writes are therefore
never applied rather than applied and undone.

**What that does not contain** is stated in the module docstring and repeated
under Risks below. This is a bound on where a run's results may land in the
repository, not a sandbox.

**`--dry-run` writes nothing at all** — no operation output and no ledger entry
on disk. It renders the entry the run would have appended through
`render_entry()`, self-checks it with `ledger.validate_entry`, and exits 0. Exit
0 there means the simulation finished, never that the operation was permitted;
the rendered entry carries the guard's verdict in its preconditions.

**Every non-dry run appends exactly one valid entry** through
`ledger.append_entry`, recording the preconditions the guard evaluated with the
guard's own ids and its refusal text, the governance records read, every path
written, the `write_scope` copied from the catalog, the kill-switch state and
promotion as the run observed them, and a reversal derived from the catalog
entry's own sentence plus the concrete paths — `rm <path>` for a file the run
created, `git checkout -- <path>` for one it changed.

With the shipped records the substrate stays inert: all five catalogued
operations refuse, no command runs, and nothing is written except the refusal
entry.

## Decisions made

- **Staging copy, not snapshot-and-revert.** Both were viable. Executing into a
  copy prevents the out-of-scope write instead of undoing it, so the repository
  is never in a state a reversal has to repair, and a deletion cannot destroy
  something the snapshot failed to capture. The cost is copying the whole tree,
  including `.git`, once per run.
- **All or nothing.** A run that broke its bound anywhere has none of its output
  applied, including the parts that were in scope. A command that wrote where it
  said it would not is not trusted about the rest.
- **A non-zero exit or a timeout applies nothing**, even when every write stayed
  in scope. Partial output from a run that did not succeed is not a result. The
  timeout is `COMMAND_TIMEOUT_SECONDS = 300`.
- **Deletions are never applied and are treated as a bound violation.**
  `write_scope` is documented as the paths an operation may *create or change*;
  no catalogued operation deletes anything; and the ledger schema requires every
  path in `paths_written` to exist for a `completed` run, so a deletion has no
  honest representation in an entry. Failing closed is the right default for the
  first version of this mechanism. An operation that must prune files needs this
  decision revisited, not worked around.
- **`.git`, `__pycache__`, and `*.pyc` are excluded from the comparison**, and
  `PYTHONDONTWRITEBYTECODE=1` is forced in the command's environment. Excluding
  them cannot weaken containment — nothing under them is ever copied back and the
  staging copy is destroyed — while including them would make every run of a
  git-reading operation look like an out-of-scope write, because reading a
  repository refreshes its index.
- **The guard is imported and called, not shelled out to.** `evaluate()` returns
  the structured decision the ledger entry needs — each precondition id with its
  result and the guard's own refusal text — which parsing rendered output would
  only approximate. The message printed and the exit code derived are exactly
  what `autonomy_guard.main()` produces from the same decision.
- **A dry run always exits 0**, including when the guard refuses. The task fixes
  both "exit 1 on refusal" and "`--dry-run` … exits 0"; a dry run reports and
  never fails a build, so the refusal is carried by the printed guard message and
  by the rendered entry's failed preconditions rather than by the exit code.
- **`--ledger-dir` was added.** Without it the safety-invariant test cannot run
  against the real repository's records without writing into `ops/ledger/`. The
  entry is always written; the option only changes where, and the CLI help says
  a run directed elsewhere is absent from the repository's audit trail.
- **`--trigger`, `--actor`, and `--as-of` were added.** The first two fill ledger
  fields the schema requires and default to `manual` / `local-operator`, or
  `scheduled-workflow` with `--trigger schedule`, which is what X5's workflow
  will pass. `--as-of` fixes the run date and the date the promotion signature is
  checked against, so tests are deterministic. `--operation`, `--root`, and
  `--dry-run` behave exactly as the plan fixes them.
- **`claimed_level` is always `A3`.** A run that reaches this script is asking to
  act without a person, whatever the answer. The schema is explicit that the
  field is the level claimed, not the level granted.
- **Precondition ids are deduplicated, and a failure wins.** The guard can record
  one id as both passed and refused — `operation-eligible` does this when a
  promotion elsewhere in the record names an ineligible operation — and the
  ledger allows one item per id. Repeated failure messages under one id are
  joined in the order the guard produced them.
- **The run id is stepped past any id already in the ledger.** See Risks: this
  works around a real collision in the shipped state rather than a hypothetical
  one.

## Risks or unresolved questions

- **CI wiring is unresolved and is not mine to fix.**
  `tests/test_contract_integration.py` requires every `scripts/*.py` to appear in
  `.github/workflows/ci.yml` or in `ValidatorWiringTests.EXEMPT` with a reason.
  Both files belong to W2. `scripts/run_unattended.py` is the fourth script to
  trip it, after `scripts/autonomy_guard.py`, `scripts/ledger.py`, and X4's
  `scripts/demotion_check.py`. It should be exempt rather than a CI step: it
  executes an operation and exits 1 whenever the substrate refuses, which is the
  shipped state, so wiring it as a step would fail every build. Suggested entry
  for W2: `"scripts/run_unattended.py": "executes one catalogued operation and
  exits 1 while nothing is promoted, which is the shipped state; its refusal and
  containment invariants are asserted by tests/test_run_unattended.py"`.
- **The bound is not a sandbox, and the docstring says so.** Only writes into the
  staging tree are contained. A command that writes to an absolute path, to
  `$HOME`, or to `/tmp`, that opens a socket, or that spawns something outliving
  it is neither stopped nor detected. The environment is inherited. The only
  resource limit is the wall-clock timeout. Containing that class of behaviour
  needs process isolation this repository does not have, and until it does, the
  answer is that such a command must not be catalogued.
- **Comparison is by content and existence, not metadata.** A change to a file's
  mode or timestamp alone is invisible, and so is a created empty directory.
- **A symlink already inside the tree that points outside it is an escape route
  the mechanism does not close.** A command following one writes outside the
  staging copy. Changed symlinks are refused on copy-back, which is not the same
  thing.
- **`ledger.next_run_id` can reissue an id that is already in use.** It reads
  entry file names, and `ops/ledger/SAMPLE_run.md` is exempt from the naming rule
  while holding `run_id: cadence-snapshot-001`, so the first real
  `cadence-snapshot` run is handed that same id; `scripts/ledger.py validate
  ops/ledger` then reports a duplicate. The runner steps over ids already
  recorded in the directory, which is why the verification run produced
  `cadence-snapshot-002`. The underlying interface belongs to X1 and is
  unchanged.
- **Running the runner against the real repository leaves a refusal entry in
  `ops/ledger/`,** which `ops/ledger/README.md` says is expected to be empty.
  That follows directly from the requirement that a refusal be recorded, and the
  two records are in tension. The verification above ran the five operations as
  specified, validated the resulting entries, and then removed them; the
  alternative, used by the tests, is `--ledger-dir` pointing at a temporary
  directory. A human should decide which of the two is the intended habit, and
  whether an inert-substrate refusal is worth committing.
- **The whole-tree copy is the dominant cost of a run** — about 13 MB and a few
  thousand files here, and it includes untracked and ignored files such as a
  local `.env`. The staging directory is `mkdtemp` (mode 0700) and is removed in a
  `finally` block, but a crash between copy and cleanup would leave a copy of the
  tree in the system temporary directory.
- **`release-brief-draft` would always be recorded `failed` if promoted.** Its
  catalogued command omits the `--since` and `--as-of` that
  `scripts/release_brief.py` requires, so it exits 2 and writes nothing. X2
  documented that deliberately in the catalog `note`; the runner surfaces it as a
  failed run rather than a silent no-op, which is the correct reading, but a
  reviewer of that dossier should know the promotion is not currently runnable.
- **`paths_read` records what the guard read plus the command's own script.** What
  the operation's command reads is not observable from here and is not recorded,
  so the field is honest but incomplete.

## Deferred opportunities

- **Real process isolation** — a container, `bwrap`, or `unshare` plus `rlimit`
  — so that the containment claim covers absolute paths, `$HOME`, and the network
  rather than only the repository tree. That is a dependency decision, not a
  tooling one, and this repository ships Python 3.11 plus PyYAML.
- **A declared read scope**, enforced the same way the write scope is, so an
  entry's `paths_read` is a bound rather than a best effort. The ladder's A0
  demotion trigger already names a run that reads outside its recorded scope.
- **Applying deletions inside the write scope**, with the ledger schema question
  it raises: a `completed` entry may not name a path that no longer exists, so
  recording a deletion needs either a new outcome or a new field.
- **`--json` output**, matching the same idea deferred by X2, if X5's workflow
  would rather read a structured result than the rendered text.
- **Recording a bounded excerpt of the command's output in the entry body.** It
  is printed to the operator today and stored nowhere; storing it means running
  the ledger's personal-data scan over text the runner does not control.
- **A per-operation rate limit.** The ladder's A3 bound names a rate and a scope
  limit. The scope half is `write_scope` and is now enforced; the rate half has
  no record to read and nothing to limit while nothing is promoted.
- **A `make run-unattended OPERATION=<id>` target**, once W2 decides where the
  substrate belongs in the check order.
