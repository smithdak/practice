## Summary

Created `templates/RELEASE_EVIDENCE.md`, a reusable, non-secret release-evidence
record that a maintainer fills in when running release validation. It captures
run identity (baseline/candidate commit IDs, date, operator role — roles, never
private individual names), the six real automated checks as a command/result/
evidence-pointer table, content-and-claim checks, agent-permission checks, the
dry-run exit summary, open holds remaining, and a human release-owner
sign-off by role and non-secret approval reference.

Every evidence field states what to record and what must not be recorded,
reusing the launch checklist red line ("never put keys, credentials, recovery
codes, participant data, or private invitation links in the evidence record").
Private evidence — access inventory, sponsor identity, personal approval
detail — stays in a private maintainer record (the private `RELEASE` maintainer
item per the maintainer runbook); the template carries only non-secret
pointers. This fulfills the L008 deferral "reusable non-secret release-evidence
record template".

## Decisions made

- Used angle-bracket placeholders (`<candidate-commit-id>`, `<YYYY-MM-DD>`,
  `<role>`) matching `templates/HANDOFF.md` conventions instead of bracketed
  uppercase tokens, so a filled copy cannot trip the release publication-token
  check if it is later committed under `release/`.
- Used `pass` / `fail` / `not-run` result fields rather than checkboxes, so the
  record cannot be "checked" without naming its evidence pointer.
- Recorded the sign-off as role + date + non-secret approval reference rather
  than a personal name, consistent with the "roles, never private individual
  names" rule for run identity.
- Pointed private evidence to the private `RELEASE` maintainer item and the
  private access inventory via the existing runbooks instead of inventing a
  new storage location.
- Scoped the template to the dry-run phase's automated, content-and-claim,
  and agent-permission checks (the sections L008's deferral named); private-
  beta and public-launch evidence records were not added.

## Risks or unresolved questions

- `--task A5` validation cannot pass until the authorized Phase 2 wiring task
  adds A5 to `tasks/manifest.json` with this output and handoff path.
- If a maintainer fills the record in and commits it under `release/`, the
  release validator's unfinished-token and publication-token checks apply;
  the angle-bracket placeholder choice avoids false failures, but a maintainer
  who leaves guidance italics in place is not blocked by validation.
- Which fields the first real release run actually needs standardization on
  can only be confirmed by using the template once; L008's original caution
  still applies to field churn.
