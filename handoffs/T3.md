# T3 Handoff

## Status

COMPLETE

## Summary

Assembling the evidence for a release brief — which commits, which artifact
paths, which handoffs back them, what is still only proposed, and which human
approvals are open — was the manual step that kept `practices/005-release-notes.md`
and `buzz/agents/RELEASE_EDITOR.md` from being usable on demand. `scripts/release_brief.py`
now performs that assembly over a git range and emits a draft brief with four
parts: what shipped, what is proposed but not tested, what is explicitly not
measured, and the human approvals still outstanding.

The generator implements the method the Practice already specifies rather than
a new one: it collects committed evidence first (Method step 2), writes one
entry per change with its pointer (step 3), and leaves the result visibly in
draft awaiting a named human release owner (step 5). It performs no step 4
verification and no step 5 approval, because both are human reads of the
pointers it produces.

Rules it enforces mechanically:

- Every line in the shipped section carries a repository path or a commit hash.
  Anything the tool cannot back with one is omitted — never guessed, never
  softened into prose. A commit whose subject names no task states that no
  handoff was matched; a named handoff that is absent is reported absent rather
  than given a status.
- Paths a later commit removed are left out, so every path pointer in a brief
  resolves at the range head.
- Front-matter `maturity` and `evidence_quality` values are quoted verbatim.
  The tool never writes a maturity change and never records a gate or hold as
  cleared; it lists only the rows of `release/OWNER_REVIEW.md` whose status cell
  records OPEN, and states that their absence from a brief is not approval.
- Output is checked against the same unfinished-token and publication-token
  rules `scripts/validate.py --release` applies before anything is written, so a
  brief cannot introduce a token that release validation would reject. Commit
  subjects are emitted inside inline code, which is how a subject containing
  such a token stays quotable without becoming a claim.
- File contents are read with `git show` at the range head, never from the
  working tree, so two runs over one range produce identical bytes even with
  uncommitted local edits. This also made the tool safe to run in this
  five-worker working tree.

`--since` is inclusive (it names the first commit of the range, not git's
exclusive `A..B` baseline); `--until` defaults to `HEAD`; `--as-of` is required
so the assembly date is always stated rather than inferred from the clock.
Outside a git checkout, on an unknown revision, on a non-directory `--root`, on
a range whose `--since` is not an ancestor of `--until`, or on a malformed
`--as-of`, the command prints one actionable message and exits 1 without
writing an output file.

`release/briefs/2026-09-02-phase-2.md` is the tool's own output over the Phase 2
range `9097a59` through `5890629` (28 commits), generated and not hand-edited; a
test compares the committed file against a fresh run and fails if they diverge.

## Decisions made

- `--since` is inclusive rather than git's exclusive `A..B` baseline. A release
  range is stated by humans as "from this commit through that one", and an
  off-by-one at the range boundary silently drops a real change from a brief.
  The help text, the directory README, and a test all state the choice.
- Pointers are rendered as inline code, not as markdown links. A brief lives at
  `release/briefs/`, so a link would need a `../../` prefix that breaks the
  moment a brief is quoted elsewhere, and inline code additionally keeps commit
  subjects out of the release token scan without altering them.
- The "proposed but not tested" and "not measured" sections are derived only
  from mechanical signals: front-matter `maturity` / `evidence_quality` values
  and Lab `artifact_type`, plus a count of lines containing the phrase "not
  measured". The brief names the mechanism so a reader can tell what the count
  is and is not evidence of. No prose is summarized or paraphrased into a claim.
- `--as-of` is required rather than defaulted to the clock, so a regenerated
  brief cannot silently acquire a new date.
- Reads go through `git show` at the range head instead of the working tree.
  This was necessary here — five workers were editing this tree concurrently —
  and it is the property that makes a brief reproducible later.

## Risks or unresolved questions

- Merge commits record no file list against their first parent, so a brief
  covering a range with merges shows those commits with a hash pointer and no
  paths. The Phase 2 range is linear and unaffected; a range spanning Phase 1's
  merge commits would show the gap. The brief states the limitation on the line
  itself rather than hiding it.
- Handoff matching depends on the `task(<id>): <description>` commit-subject
  convention. A commit that changed real artifacts under a different subject
  form (`c2a10c0` in the Phase 2 range) still appears with its hash and paths,
  but carries no handoff pointer.
- The "not measured" line count is a text signal, not a semantic one: it finds
  the phrase, including inside a sentence that says a thing *is* measured
  elsewhere in the same line. It is a pointer for a human to open, which is how
  the brief describes it.
- The Phase 2 brief and one smoke test name the commits `9097a59` and `5890629`
  directly. If that history is ever rewritten, the test skips (when the commits
  are absent) or fails on the committed brief (if they change), which is the
  intended signal rather than a silent stale file.
- Nothing here clears an owner gate or an operating hold, and no `maturity` or
  `evidence_quality` field was changed. Every row in `release/OWNER_REVIEW.md`
  remains as that file records it.

## Deferred opportunities

- A `--label` flag so the brief's title can carry the human name of the range
  ("Phase 2") instead of only its as-of date; the filename carries the label
  today.
- A checker that fails when a file under `release/briefs/` differs from what the
  generator produces for its stated range, generalizing the single committed
  brief's test so the rule holds for every future brief without a per-file test.
- Grouping the shipped section by task wave or by artifact type rather than by
  commit, which would make a 28-commit brief easier to skim; it needs a source
  of truth for wave membership that is not the commit subject.
- Emitting the Release Editor's completion-gate block (`Artifact:` /
  `Status evidence:` / `Source state:` / `Evidence state:` / `Limits:`) per
  entry, so a drafting agent receives the gate pre-filled from committed
  evidence rather than reconstructing it.
