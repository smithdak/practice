## Summary

`ops/METRICS.md` defined a measurement contract with no collector, so every
count was made by hand and the repository side of the contract was invisible
between manual reviews. This task adds `scripts/collect_metrics.py`, a
deterministic offline collector for the part of that contract committed files
can actually answer, plus its tests and an operating README.

The collector reports five things from committed files: artifact inventory by
type, declared state, capability stage, and declared evidence-quality label;
evidence coverage against the evidence elements the contract names; accepted
contribution records taken from dated artifact changelog entries; owner gates
and operating holds recorded in `release/OWNER_REVIEW.md`; and internal link
health. Every count is printed with its denominator and its evidence coverage.

Seven parts of the contract cannot come from committed files — Activation,
proposed Contribution, Artifact reuse, Implementation, Response quality,
Retention, and Maintainer health. Each is printed as `not collected` with the
reason and the human route from "Minimal manual measurement at launch". None is
printed as `0`, so a measured zero and an unmeasured metric stay distinguishable
in both the markdown and the JSON output.

"Data not to collect" is honored in code, not only in prose. The collector has
no data structure for a person, never enters `.git` (so authorship, names, and
addresses are unreachable), imports no network or subprocess module, and reads
only files under the root it is given. It reads `maturity` and
`evidence_quality` labels and never writes them, and it copies gate and hold
statuses verbatim rather than asserting that anything is cleared.

Front matter is parsed by reusing `scripts/validate_artifacts.py` and link
targets by reusing `scripts/check_links.py`, so no second parser was introduced
that could drift from the validators.

Output is markdown to stdout by default, `--out <path>` to write a report,
`--json` for machine consumption, and `--as-of YYYY-MM-DD` with stable sorting
throughout so two runs over the same tree produce identical bytes. No dated
report was generated into the tree; `ops/metrics/README.md` documents how to
produce one and where to keep it.

## Decisions made

- Accepted contributions are counted from dated bullets under an artifact's
  `## Changelog` heading. That is the only contribution evidence a committed
  file can supply; proposed contributions live in issues and pull requests and
  are reported as not collected rather than approximated.
- The contract's evidence elements (inputs, steps, output, evaluation,
  limitations, failure modes, inspectable record) are mapped onto the headings
  each artifact type's schema actually defines, since the element names are not
  headings. The map is published in `ops/metrics/README.md` so a reader can see
  what a coverage number means. A Guide is scored on four elements because its
  schema has no limitations or failure-modes section; the denominator states
  that instead of counting the absent sections as gaps.
- A section that exists but is empty does not count as a stated element.
- Owner gates and operating holds are read from the tables in
  `release/OWNER_REVIEW.md` and reported as "recorded open", with any other
  status copied verbatim and labeled as the packet's wording. The collector
  never says a gate is cleared. When the packet or its tables are absent, the
  section prints as not collected rather than as zero open gates.
- The collector exits 0 whenever it produces a report and 2 only for usage
  errors. It describes state; the validators remain the things that fail a
  build.
- Reports are generated on demand and not committed. The README gives the
  command, the `git rev-parse HEAD` step that pins a report to a commit, and an
  out-of-tree destination.

## Risks or unresolved questions

- The heading map is the load-bearing definition of evidence coverage and it
  can go stale. If a schema renames a section, coverage falls with no content
  change. The README names this failure mode and says to update the map in
  `scripts/collect_metrics.py` and the README table in the same change; nothing
  currently enforces that pairing automatically.
- For a Practice, the `limitations` element maps to `Problem and scope` or
  `Use when`, both of which the schema already requires. That element is
  therefore close to always satisfied and carries little signal today. It is
  reported per element so a reader can see which elements are doing the work.
- Gate and hold parsing depends on the heading text ("Owner gates",
  "operating holds") and on the status cell being the last column of the table
  in `release/OWNER_REVIEW.md`. A restructure of that packet turns the section
  into `not collected`, which is visible in the report but is a maintenance
  coupling. A row-count drift check against `OWNER_GATES.md` is included and is
  currently silent (8 rows in both).
- The collector covers one of the three evidence sources the contract names.
  It cannot make the launch measurement route real, and the operating hold on
  evidence-ready launch measurement is untouched by this work.

## Deferred opportunities

- A period-over-period diff mode that compares two JSON reports and prints what
  moved, with an explicit note when the method changed between them.
- A CI job that runs the collector and fails only on a drop in evidence
  coverage, once maintainers agree what a drop should block.
- A schema-derived heading map, generated from `docs/schemas/` rather than
  restated in the collector, which would remove the staleness risk above.
- An optional reader for a human-maintained aggregate ledger, so a single report
  could show the Git-side counts and the human-side counts together. This needs
  a ledger format decision that belongs to the maintainers, and the ledger
  itself stays private and access-controlled.
- A `make metrics` target. The Makefile is outside this task's owned paths.
