## Summary

Created the private-beta operating kit and the repository issue-triage policy.
`ops/BETA_OPS.md` gives the first-cohort operators a daily pass layered on the
weekly cadence, a roles table (roles, not names), step-by-step private intake

maintainer-versus-agent boundaries, and how the Lab/Practice/Project/Story

## Decisions made

- Wrote the triage policy at `.github/TRIAGE_POLICY.md` rather than the
  `.github/ISSUE_TEMPLATE/triage-policy.md` path listed in
  `SWARM_PHASE2_PLAN.md`; the tasking specified the former, and a policy
  document does not need to sit beside the form files.
- State labels reuse the practice's exact state names (`needs-info`,
  `ready-for-agent`, `ready-for-human`, `wontfix`), so the label set is the
  state machine instead of a parallel vocabulary; routing rules are referenced
  from `practices/004`, not duplicated.
- Response-time expectations are framed as beta-period expectations reviewed
  at the day-30 checkpoint, not service-level commitments, respecting the
  recorded deferral of measured queue service levels.
- The facilitation prompt backlog is a scaffold only: entry record, source
  rule, approval/posting flow, and retirement rule. No example prompts or
  replies were invented, honoring the B004 deferral.
- Kept the existing form-set labels (`lab`, `practice`, `project`, `story`,
  `proposal`) and added only four state labels, two category labels, and one
  optional `blocking` label.

## Risks or unresolved questions

- Labels do not exist in GitHub yet: the repository destination is an open
  owner gate, so label creation is a human setup action recorded in the beta
  checklist.
- O5 is not present in `tasks/manifest.json`, so task-scoped validation
  (`--task O5`) is not applicable; repository validation was run instead.
- The daily beta pass adds a rhythm beyond the weekly cadence; if the beta
  ends without an explicit offboarding, the pass could linger. The kit states
  it is dropped at beta end, but nothing enforces that.

## Deferred opportunities

- Facilitation prompt content and sanitized example replies, once real beta
  questions exist.
- Measured queue service levels and cadence revision after real beta data
  (existing L007 deferral).
- A GitHub Action or bot that nags stale `needs-info` check points — needs the
  repository destination first, and triage automation should stay
  label-and-comment only.
- Per-form routing refinements (for example, a dedicated Note intake form)
  if beta volume shows the four forms are insufficient.
