## Summary

`.github/workflows/unattended.yml` is the scheduled half of the A3 substrate: the
only thing in the repository that can start an operation without someone typing a
command. It is inert as shipped, and it never pushes to the default branch.

**Two jobs, and the second one does not start today.** Job `guard` holds a
read-only token, discovers every operation id from `ops/autonomy/operations.yaml`,
and runs `scripts/autonomy_guard.py` once per id. With the shipped records it
gets five refusals, writes each refusal and its failed preconditions to the run
summary, publishes an empty `permitted` output, and exits 0. Job `propose` is
gated on `needs.guard.outputs.permitted != ''`, so in the shipped state it never
starts and the workflow never holds a token that can write anything. A refusal is
the expected weekly outcome, and the run is green; if this workflow goes red,
something is actually wrong.

**Nothing is hardcoded.** The operation list is read from the catalog, so signing
a promotion or adding a catalogued operation changes what the workflow attempts
without anyone editing the workflow. The design has exactly two records — a
signed promotion and the kill switch — and this file is deliberately not a third.

**What an unattended run arrives as.** Job `propose` creates a branch named
`unattended/<date>-<run id>-<attempt>`, runs each permitted operation through
`scripts/run_unattended.py --trigger schedule --actor scheduled-workflow`, and
opens one pull request per run. The branch is new every run, so no push here can
ever be a force-push, and nothing in the job names the default branch as a push
target. The pull request body carries every ledger entry the run appended, in
full, plus the exact reversal commands: `gh pr close <number> --delete-branch`
before merge, and a `git revert` of the merge commit after. The body is finished
with a second `gh pr edit` call because the pull request's number does not exist
until it is created, and a reviewer should not have to work out the undo.

**Three deliberate refusals to act.**

- **No auto-merge.** Amendment 001 made bounded merge eligible, not promoted and
  not catalogued. The workflow implements none, and a comment says why.
- **A self-modification backstop.** Before anything is pushed, the job refuses to
  open a pull request if the run changed any path under `.github/`,
  `ops/autonomy/`, `scripts/`, `tests/`, `tasks/`, `buzz/agents/`,
  `docs/framework/`, `docs/schemas/`, `handoffs/`, or the locked decision records.
  `ops/ledger/` is deliberately excluded from that list: no operation may write
  there, but the runner writes one entry per run there and that record is the
  thing being proposed. This is a backstop, not the bound — the runner's staging
  copy and the guard's write-scope check are the bound — and it is here because
  amendment 001 states the exclusion is not waivable by a promotion.
- **`fetch-depth: 0` on both checkouts.** X6 verified that in a `--depth 1` clone
  `scripts/cadence.py` collapses all six pass dates onto the clone's tip commit
  and prints no warning, so a scheduled cadence report would be quietly wrong for
  as long as nobody checked it by hand.

`ops/autonomy/PR_REVIEW_CONTRACT.md` states what a reviewer of one of these pull
requests is agreeing to. Its first section says plainly that no such pull request
can exist today, and that one appearing while the switch is engaged is a security
finding rather than a review. Its central claim is that **merging accepts the
content, not the process**: everything upstream of the pull request is mechanical,
and mechanical checks are the ones that pass while a file says something wrong. It
lists what the guard, the runner, and the ledger already checked so a reviewer
does not redo it; five things to check in order, of which only step 3, is the
content true, needs a human; seven conditions that make a pull request closeable
without discussion; and the rule that an unattended pull request still open when
the next scheduled run fires is closed unreviewed by whoever notices first, with
re-engaging the kill switch as the escalation when that happens twice running.

### What cannot be verified until an owner enables it

Stated plainly, because the rehearsals above are convincing enough to be
mistaken for a working pipeline.

1. **No step of this workflow has ever run on GitHub.** Everything above ran on
   this machine with a stubbed `gh`, a local bare repository standing in for
   `origin`, and a hand-written driver substituting the `${{ }}` expressions. The
   Actions expression syntax, `actions/checkout@v4` with `fetch-depth: 0`,
   `actions/setup-python@v5`, `$GITHUB_STEP_SUMMARY` rendering, and job-to-job
   outputs are unexercised.
2. **`gh pr create` is unproven, and will fail until a repository setting is
   turned on.** Opening a pull request from a workflow needs Settings → Actions →
   General → Workflow permissions → **"Allow GitHub Actions to create and approve
   pull requests"**, which is off by default and is an owner decision. With it
   off, `gh pr create` fails with "GitHub Actions is not permitted to create or
   approve pull requests" even though the token carries `pull-requests: write`.
   The workflow comments say this; nothing in it can turn the setting on.
3. **The `permissions` block is unproven against a real token.** `contents: write`
   plus `pull-requests: write` is the documented minimum to push a branch and open
   a pull request, but whether that is sufficient here depends on the repository's
   default `GITHUB_TOKEN` permissions and on branch protection rules, neither of
   which is visible from the repository contents.
4. **The cron has never fired.** `23 6 * * 1` is unexercised, and GitHub disables
   a scheduled workflow after 60 days with no repository activity.
5. **The permitted path has never run with a real promotion**, because none has
   been signed. Every rehearsal of it used a promotion I wrote into a throwaway
   copy and deleted with the copy; `ops/autonomy/promotions.yaml` in this
   repository is untouched and still reads `kill_switch: engaged` with
   `promotions: []`.

The first live exercise should be a `workflow_dispatch` with `dry_run` left at its
default `true`. That reaches the guard, produces the refusal summary, and cannot
open a pull request or write a file.

## Decisions made

- **Weekly, Mondays 06:23 UTC.** `ops/WEEKLY_CADENCE.md` makes the operating loop
  weekly with a Monday intake window, and every catalogued operation is an input
  to that window. More often would open pull requests faster than the window that
  reads them, and a queue of unread machine pull requests is worse than none —
  which is why the review contract closes stale ones rather than letting them
  accumulate. Less often would let a drift or staleness finding sit for more than
  one cadence. 06:23 rather than 06:00 because GitHub delays jobs queued on the
  hour, and a report claiming to describe Monday is less useful on Tuesday.
- **Two jobs rather than one.** Splitting the guard from the run is what lets the
  shipped state never grant a write token at all. The cost is a second checkout.
- **The workflow does not append a ledger entry for a refusal.** The runner does,
  but the workflow asks the guard directly and never reaches the runner when
  nothing is permitted. Running the runner over all five operations weekly would
  commit five refusal records a week — noise that would bury the entries that
  record something happening. A scheduled refusal is recorded in the workflow run
  summary and log instead. This trades a durable record for a legible one; see
  Risks.
- **One pull request per run, not per operation.** A run is the unit a reviewer
  can reason about, and the branch is the unit that gets closed.
- **A failing operation does not stop the loop.** What earlier operations produced
  is still proposed, the failed run's ledger entry still lands in the pull
  request, and a final step fails the job so the failure is visible. A failure
  that quietly discarded the record would be the worse trade.
- **`--actor scheduled-workflow` regardless of trigger.** The workflow is what
  executed the operation; `--trigger` records whether a clock or a person started
  it. The runner records roles, never people.
- **The review contract's staleness rule is "close it", not "review it faster".**
  Two consecutive cycles of unreviewed pull requests is a signal to re-engage the
  kill switch or withdraw the promotion, not to try harder.

## Risks or unresolved questions

- **A scheduled refusal is durable only in GitHub's log retention.** Workflow logs
  and run summaries expire (90 days by default, and sooner if a repository setting
  says so). If someone later asks "did the substrate refuse every week in
  October", the answer lives in a log that may be gone. Closing this means either
  appending refusal entries to the ledger — which trades legibility for durability
  — or a periodic summary record. Not decided here.
- **The self-modification backstop is a hardcoded list.** It repeats, in shell,
  paths that `scripts/autonomy_guard.py` already holds in `GOVERNED_PATHS` and
  `GOVERNED_PREFIXES`. Two copies of a list drift. The lists agree today, minus
  `ops/ledger/` which the backstop must allow, but nothing checks that they still
  agree — no test asserts it, and neither file mentions the other's copy. A test
  in W2's `tests/test_contract_integration.py` could.
- **The workflow is unwired from CI.** Nothing validates that this file parses,
  that its script paths exist, or that its flags are spelled correctly. It is not
  in the release validator, `check_links.py` does not read YAML, and
  `tests/test_contract_integration.py` reads only `ci.yml`. A typo in a script
  path here would be found by the first scheduled run, months from now. That
  wiring belongs to W2 and to `.github/workflows/ci.yml`, neither of which I own.
- **`github.event.repository.default_branch` is the base branch, and it is read
  from the event payload rather than from the repository.** It is correct for
  `schedule` and `workflow_dispatch`, but if it were ever empty, `gh pr create
  --base ""` would fail rather than target the wrong branch, which is the right
  failure direction but not one I could exercise.
- **The pull request body embeds ledger entries in a five-backtick fence.** An
  entry containing a five-backtick line would break the rendering. The runner's
  generated bodies contain no fences at all, and a hand-written one is not
  possible on this path, so this is theoretical — but it is a rendering assumption
  rather than an enforced one.
- **Nothing enforces the review contract.** It is a document. A reviewer who
  merges without reading step 3 leaves no trace of having skipped it, and the
  ledger entry cannot record whether a human actually checked the content.
- **The `propose` job re-checks out at the tip of the default branch**, which may
  have moved since the `guard` job read `promotions.yaml`. A promotion withdrawn
  between the two jobs would be honoured, because the runner asks the guard again
  in the second job — but a promotion *added* between them would not be picked up
  until the next run, which is the safe direction.

## Deferred opportunities

- **Wire `scripts/demotion_check.py` into this workflow.** X4's checker evaluates
  the ladder's demotion triggers against the ledger and the working tree. Running
  it after each unattended run, and re-engaging the kill switch or failing loudly
  on a trigger, would close the loop between acting and being demoted for it. It
  is not here because the demotion check's own wiring belongs to W2 and because a
  workflow that could edit `promotions.yaml` would violate the self-modification
  exclusion — the honest form is a failed run and an alert, not an automatic edit.
- **A `--list` mode on the guard or the runner.** The discovery step reads the
  catalog with an inline Python snippet. A `scripts/autonomy_guard.py --list`
  emitting the catalogued ids would put that parsing next to the code that already
  validates them, and would let the workflow stop parsing YAML itself.
- **A CI check that the workflow's script paths and flags exist.** A small test
  that loads every `.github/workflows/*.yml`, extracts `python3 scripts/...`
  invocations, and asserts each script exists and accepts each flag. It would have
  caught nothing today, which is the point: it catches the edit made in six
  months.
- **A repository-settings checklist for the owner.** The pull-request setting named
  above, `GITHUB_TOKEN` default permissions, and branch protection are three
  owner-side facts this workflow depends on and cannot see. They belong in the
  owner review packet or the beta operating kit, not in a workflow comment.
- **Auto-delete merged branches.** A repository setting, not a workflow change,
  and it would keep the disposable branches from accumulating. Deliberately not
  assumed: the reversal commands use `--delete-branch` explicitly instead.
