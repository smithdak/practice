## Summary

The operating loop in `ops/WEEKLY_CADENCE.md` was prose only: to know what was
due, a maintainer had to read the document and work it out by hand against the
repository. T1 makes that computation runnable without moving any decision to
an agent.

`ops/cadence.yaml` is a machine-readable index of the loop. It mirrors the six
passes (Intake, Build, Review, Release, Practice Session, Maintenance) and the
four continuous queues the cadence document already defines, adds none of its
own, and cites the section each entry was read from. Every pass carries `id`,
`name`, `rhythm`, `named_output`, `owner_role` (a role, never a person),
`skip_rule`, and repo-relative evidence globs, plus the off-repository records
(Git issues, pull requests, the private maintainers queue, Buzz threads) that
no script can see.

`scripts/cadence.py` prints a deterministic offline report: per pass, when its
named output last changed, whether its window has elapsed, and which evidence
globs matched nothing; then the three queue checks the repository can actually
support — handoffs recorded `BLOCKED`, owner gates and operating holds recorded
`OPEN` in `release/OWNER_REVIEW.md`, and markdown files whose `As of:` date is
older than the staleness limit. The report opens with its own limits: it reads
this repository only, knows nothing about Buzz channel activity, treats an
elapsed window as a window rather than as overdue work for a named person, and
clears no gate or hold.

`tests/test_cadence.py` covers the due/not-due rules, both queue checks, the
staleness rule, the `--json` shape, configuration errors, the git-dated path,
the no-git degradation path, and a smoke test against this repository.

## Decisions made

- `interval_days` is a machine translation of a rhythm phrase, not a new
  commitment: 7 days for Intake, Build, and Review; 30 for Maintenance
  ("last Friday or next available pass"). The file says so in a header comment.
- Release and Practice Session use `due_rule: on_trigger`, so elapsed time
  never makes them due. That follows the cadence document's own distinction:
  "A release or Session happens only when its packet is ready and a human
  approves it."
- The staleness rule is imported from `scripts/check_links.py` rather than
  reimplemented, and `staleness_limit_days` in the index must equal that
  module's `STALE_LIMIT_DAYS`. A mismatch is a configuration error with a
  message saying to change one rule, not two.
- Open owner gates and operating holds are reported under the cadence
  document's "Stop and escalate" section rather than being forced into one of
  the four continuous queues, none of which covers reserved human decisions.
  The report repeats each recorded status verbatim and states that it clears
  nothing.
- Last-changed dates come from one `git log` call. Outside a git checkout, or
  when git is missing or errors, every date is reported as `unknown` and no
  window is computed. There is deliberately no file-modification-time fallback:
  in a fresh checkout that would report today's date for every file.
- Configuration validation rejects an `owner_role` containing the founder's
  name, so the "role, never a personal name" rule is machine-checked.
- Evidence globs point at where a pass's output lands in this repository; each
  pass also lists `off_repo_records` for readers, which no script checks. The
  Session pass carries a note that its evidence path is the session operating
  record, so a change to it does not mean a Session ran.
- The report is not wired into CI. It is a status report, not a gate, and
  making it a required check would turn "the window elapsed" into a build
  failure that no person owns.

## Risks or unresolved questions

- `ops/cadence.yaml` is a mirror, and only its section citations are checked
  against `ops/WEEKLY_CADENCE.md`. If someone adds a seventh pass to the
  document and forgets the index, the report silently omits it. A stronger
  drift check would have to parse the weekly-loop table.
- Several evidence globs cover directories that other work also touches
  (`ops/*.md`, `reviews/*.md`, `handoffs/*.md`). A pass can therefore look
  fresh because a neighbouring file changed, not because the pass ran. The
  report shows per-glob newest dates in `--json` so a reader can check.
- In a shallow clone (`actions/checkout` defaults to depth 1) `git log` sees
  one commit, so every file reports that commit's date. The report would then
  show all passes as changed on the same day. Nothing in the script can detect
  this; a maintainer reading a shallow checkout should treat the dates as
  unreliable.
- `T1` is not in `tasks/manifest.json`, so `scripts/validate.py --task T1` is
  not applicable; repository-wide and release validation were run instead.
- Validation was run against a working tree that five other Phase 3 workers
  were editing concurrently. All commands passed at the time of writing; file
  counts in the results above will move as their work lands.

## Deferred opportunities

- A `--pass <id>` filter and a `--only-due` flag, once someone runs the report
  often enough to want a narrower view.
- A weekly informational CI job that prints the report as a job summary. It
  must stay non-blocking, for the reason recorded above.
- Reading Git issue and pull-request state from an offline export, so the
  Intake and Review passes can report the records that actually hold their
  output. This needs a repository destination, which is an open owner gate.
- A `--check` mode that exits non-zero on a blocked handoff or an elapsed
  window. Deliberately not built: it would make an agent's report look like an
  operating gate.
- Recording the cadence report itself as maintenance-pass evidence, once a
  human maintainer decides whether a generated report belongs in Git.
